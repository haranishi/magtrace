# MAGTRACE 要件定義書

- 文書ID: MAGTRACE-REQ-001
- バージョン: 0.3
- 作成日: 2026-08-29
- ステータス: UX改善ハーネス・Figma v0.2検証済み、実装レビュー待ち

## 1. 要件概要

### 1.1 背景・目的

SNSで見つけた言葉について、現在の意味だけでなく「いつから、どのような文脈で雑誌に登場してきたか」を短時間で把握できる場所がない。一般的な検索は個々の記事を一覧表示するが、社会的関心の時間変化を理解しにくい。

MAGTRACEは、雑誌記事の書誌メタデータを年代別に整理し、キーワードの掲載傾向と代表的な記事を可視化するWebアプリである。

プロダクトの一文説明:

> 気になる言葉を入力すると、その言葉が雑誌でいつ・どのように語られてきたかを確認できる「雑誌版Googleトレンド」。

### 1.2 解決する課題

- SNS上の短い情報だけでは、言葉の歴史や文脈を把握しづらい。
- 雑誌記事を年代横断で調べるには、検索と整理に時間がかかる。
- AI生成の説明では、根拠となる原典や収録範囲を確認しづらい。
- 学生・クリエイター・企画職が、調査の入口として使える視覚的な資料が少ない。

### 1.3 対象ユーザー

#### プライマリーペルソナ

- 18〜35歳の学生、SNSクリエイター、編集・企画・マーケティング担当者
- SNSで見つけたテーマを、企画・投稿・レポートの題材として調べる
- 専門データベースの操作には慣れていないが、出典の信頼性を重視する

#### セカンダリーペルソナ

- カルチャー・流行・言葉の変化に興味がある一般ユーザー
- 自分の生まれた年や懐かしい時代の雑誌記事を楽しみたいユーザー

### 1.4 スコープ

#### MVP対象

- 日本語キーワードによる雑誌記事メタデータ検索
- 年代区分ごとの掲載件数表示
- 代表的な記事タイトル、雑誌名、発行日、著者の表示
- 年代フィルター
- NDLサーチ等の原典ページへのリンク
- 検索結果の共有URL
- SNS共有用サマリーカード
- データ提供元、ライセンス、収録範囲の明示
- APIレスポンスのサーバー側キャッシュ

#### MVP対象外

- 雑誌本文の取得、転載、生成AIによる本文要約
- 雑誌表紙の無許諾表示
- ユーザーアカウント、フォロー、コメント
- 「社会全体での初出」など、API収録範囲を超えた断定
- 有料課金、広告表示
- 出版社別の販売・在庫検索

### 1.5 前提・制約

- 初期公開は無料、広告なし、個人運営を想定する。
- 中核データは国立国会図書館雑誌記事索引 `zassaku` と `zassaku-online` のメタデータに限定する。
- 結果には「NDLサーチAPIの収録範囲内」という注記を常時表示する。
- NDLおよびデータ提供機関のクレジットとCC BYライセンスへのリンクを表示する。
- 継続的なAPIアクセスを開始する前に、NDLサーチAPI利用申請フォームから利用内容を連絡する。
- APIはブラウザから直接呼ばず、サーバーAPI経由で呼び出す。
- 同一検索条件はキャッシュし、外部APIへの重複アクセスを避ける。
- 商用化時は、利用対象データと最新利用条件を再監査する。

## 2. API選定

### 2.1 採用API

#### EXT-API-001: NDLサーチAPI

- 用途: 国内雑誌記事の検索、書誌情報、年代別件数の取得
- データプロバイダ: `zassaku`, `zassaku-online`
- 認証: 不要
- 通信: HTTPS
- 形式: OpenSearch XML / SRU XML
- 利用条件: 検索API・ハーベストAPI対象。非営利・営利とも利用可。メタデータはCC BY。
- 必須対応:
  - クレジット表示
  - ライセンス表示
  - キャッシュ
  - 過負荷を避ける逐次実行とバックオフ
  - 継続利用時の連絡
- 公式仕様: https://ndlsearch.ndl.go.jp/help/api/specifications
- データ提供条件: https://ndlsearch.ndl.go.jp/help/api/provider
- 利用案内: https://ndlsearch.ndl.go.jp/help/api

#### EXT-API-002: Crossref REST API（Phase 2候補）

- 用途: 学術雑誌モードでの論文・ジャーナルメタデータ補完
- 認証: Publicは不要。Polite poolでは連絡先を指定する。
- 形式: JSON
- 利用条件: メタデータは原則自由に再利用可能。abstractは権利条件が異なるためMVPでは取得・表示しない。
- 実装条件: User-Agent / `mailto`、キャッシュ、レート制限・429へのバックオフ
- 公式仕様: https://www.crossref.org/documentation/retrieve-metadata/rest-api/

### 2.2 不採用・保留API

#### Google Books API

- `printType=magazines` は利用可能だが、APIキー、クォータ、画像利用条件の追加管理が必要。
- 表紙画像を使わないMVPでは便益が小さいため保留する。

#### 楽天ブックス雑誌検索API

- 販売中雑誌の情報には適するが、App ID・Access Key管理、ブランド表示、商品導線が必要。
- 研究・発見中心のMVPから外れやすいため、購入導線を検討するPhase 3まで保留する。

### 2.3 API利用判断

MVPはEXT-API-001のみで成立させる。API利用料と秘密鍵を不要にし、権利範囲を雑誌記事メタデータに限定する。Crossrefは学術誌モードを追加する場合のみ採用する。

利用条件確認日: 2026-08-29。NDLサーチの公式API仕様・データプロバイダ一覧・利用案内を確認し、`zassaku` と `zassaku-online` は非営利・営利の検索API利用が許可され、メタデータの利用条件がCC BYであることをMVP採用の根拠とした。公開前に継続利用の連絡、表示クレジット、キャッシュ、バックオフを実装チェックリストで再確認する。

## 3. ユーザーストーリー

### US-001: キーワードを検索する

**As a** SNSで気になる言葉を見つけたユーザー,
**I want to** 言葉をそのまま入力して検索したい,
**So that** 雑誌で語られてきた履歴をすぐ確認できる。

**受け入れ条件:**

- [ ] AC-001-1: 1〜50文字の日本語・英数字を入力できる。
- [ ] AC-001-2: Enterキーまたは検索ボタンで実行できる。
- [ ] AC-001-3: 前後空白、連続空白、全角・半角差を正規化する。
- [ ] AC-001-4: 未入力時は送信せず、入力欄に説明を表示する。
- [ ] AC-001-5: ローディング中であることを画面上で確認できる。

**優先度:** P0  
**見積もり:** M

### US-002: 掲載傾向を時系列で理解する

**As a** 企画やレポートのテーマを調査するユーザー,
**I want to** 年代別の掲載件数をグラフで見たい,
**So that** 増減や注目された時期を短時間で把握できる。

**受け入れ条件:**

- [ ] AC-002-1: 初期表示では5年単位または10年単位の件数を表示する。
- [ ] AC-002-2: グラフの各点はキーボードとタッチで選択できる。
- [ ] AC-002-3: 色だけに依存せず、数値と期間ラベルを表示する。
- [ ] AC-002-4: 「API収録範囲内の件数」であることをグラフ付近に表示する。
- [ ] AC-002-5: データ不足時は推移を断定しない。

**優先度:** P0  
**見積もり:** L

### US-003: 代表記事を確認する

**As a** 検索結果の背景を知りたいユーザー,
**I want to** 各年代の代表的な記事タイトルを見たい,
**So that** 数字の変化がどのような内容によるものか確認できる。

**受け入れ条件:**

- [ ] AC-003-1: 記事タイトル、雑誌名、発行日、著者を表示する。
- [ ] AC-003-2: 欠損項目は「不明」とせず、項目自体を省略する。
- [ ] AC-003-3: 代表記事の選定基準を説明できる。
- [ ] AC-003-4: 記事カードから出典詳細へ移動できる。

**優先度:** P0  
**見積もり:** M

### US-004: 原典を確認する

**As a** 出典を重視するユーザー,
**I want to** NDLサーチ上の原典情報を開きたい,
**So that** レポートや企画で根拠を確認できる。

**受け入れ条件:**

- [ ] AC-004-1: 外部リンクであることを明示する。
- [ ] AC-004-2: 出典名、データ提供機関、ライセンスを表示する。
- [ ] AC-004-3: リンク切れ時も、取得済みの書誌情報は確認できる。

**優先度:** P0  
**見積もり:** S

### US-005: 発見を共有する

**As a** 面白い変化を見つけたユーザー,
**I want to** 出典付きの結果カードを共有したい,
**So that** SNS上で根拠を保ったまま話題にできる。

**受け入れ条件:**

- [ ] AC-005-1: キーワード、期間、件数推移、サービス名を含むカードを生成する。
- [ ] AC-005-2: 「NDLサーチAPI収録範囲内」の注記を削除できない。
- [ ] AC-005-3: 共有URLから同じ検索条件を再現できる。
- [ ] AC-005-4: Web Share API非対応環境ではURLコピーへフォールバックする。

**優先度:** P1  
**見積もり:** M

### US-006: 年代を絞り込む

**As a** 特定時期を詳しく調べたいユーザー,
**I want to** 対象年代を選択したい,
**So that** 関心のある期間の記事だけを比較できる。

**受け入れ条件:**

- [ ] AC-006-1: 開始年・終了年を選択できる。
- [ ] AC-006-2: 不正な期間指定を防止する。
- [ ] AC-006-3: フィルター状態をURLに保持する。

**優先度:** P1  
**見積もり:** S

### US-007: 結果がない・取得できない場合に回復する

**As a** 検索に失敗したユーザー,
**I want to** 次にできることを知りたい,
**So that** 行き止まりにならず再検索できる。

**受け入れ条件:**

- [ ] AC-007-1: 0件時は表記変更例と検索候補を表示する。
- [ ] AC-007-2: APIエラー時は再試行と検索語変更を提示する。
- [ ] AC-007-3: キャッシュがある場合は取得日時付きで表示する。
- [ ] AC-007-4: エラー詳細や内部URLを画面へ露出しない。

**優先度:** P0  
**見積もり:** M

### US-008: データの限界と利用条件を理解する

**As a** 結果を引用するユーザー,
**I want to** 収録範囲とライセンスを確認したい,
**So that** 数値を誤って社会全体の傾向として扱わずに済む。

**受け入れ条件:**

- [ ] AC-008-1: 全結果画面に収録範囲注記を表示する。
- [ ] AC-008-2: 「最古」ではなく「収録データ上で最も古い」と表現する。
- [ ] AC-008-3: データ出典・CC BY・更新日時を確認できる。

**優先度:** P0  
**見積もり:** S

### US-009: 関連する文脈を掘る

**As a** 言葉の広がりを調べるユーザー,
**I want to** 一緒に登場する言葉や上昇中の関連語を選びたい,
**So that** 最初に思いつかなかった社会的な文脈まで探索できる。

**受け入れ条件:**

- [ ] AC-009-1: 分析結果に「上昇中」と「一緒に出る」を区別して表示する。
- [ ] AC-009-2: 関連語ごとに変化率または共起件数と短い説明を表示する。
- [ ] AC-009-3: 関連語を選択すると、その言葉を検索条件にした分析へ遷移する。
- [ ] AC-009-4: 関連語がない場合は無理に生成せず、別の検索候補を提示する。

**優先度:** P1  
**見積もり:** M

### US-010: 2つの言葉を比較する

**As a** 企画仮説を検証するユーザー,
**I want to** 2つの言葉の掲載推移を同じ期間で比較したい,
**So that** 話題化の時期や文脈の違いを判断できる。

**受け入れ条件:**

- [ ] AC-010-1: 分析画面から比較語を1つ追加できる。
- [ ] AC-010-2: 2系列を色だけでなく線種、ラベル、表形式でも識別できる。
- [ ] AC-010-3: 比較期間と検索条件を共有URLへ保持する。
- [ ] AC-010-4: 比較語を解除し、単独分析へ戻れる。

**優先度:** P1  
**見積もり:** L

## 4. 機能要件

### FR-001: 検索クエリ処理

- 入力: `q`, `from`, `until`, `source`
- 処理: 正規化、危険文字除去、長さ検証、キャッシュ照合、外部API呼び出し
- 出力: 正規化クエリ、総件数、期間別件数、代表記事、出典情報、取得日時
- エラー: 400（不正入力）、429（アプリ側制限）、502（外部API障害）、504（タイムアウト）

### FR-002: トレンド集計

- 初回は大きい年代区分で件数を取得する。
- ユーザーが年代を選択した場合のみ細かい粒度を取得する。
- 検索条件ごとに24時間以上キャッシュする。
- 同一キーへの同時リクエストは1本に集約する。
- 件数は「NDL収録範囲内のヒット件数」として扱う。

### FR-003: 代表記事選定

- 各年代から最大3件を表示する。
- 取得順を「社会的代表性」と誤認させない。
- 初期MVPでは検索適合度または発行日順を使用し、UIに選定基準を表示する。

### FR-004: 共有URL

- URL例: `/topics/%E6%8E%A8%E3%81%97%E6%B4%BB?from=2000&until=2026`
- canonical URLを設定する。
- 検索条件のみをURLに保存し、外部APIの生レスポンスを含めない。

### FR-005: クレジット表示

- フッターと結果画面にNDLサーチAPI利用表記を表示する。
- `zassaku` / `zassaku-online`、提供機関名、CC BY 4.0へのリンクを表示する。
- 共有カードにも短縮クレジットと収録範囲注記を表示する。

### FR-006: 検索履歴

- 直近5件を端末のlocalStorageに保存する。
- サーバーに個人を識別できる検索履歴を保存しない。
- ユーザーは履歴を一括削除できる。

### FR-007: 関連文脈

- 記事タイトル内の語の共起件数と期間別増減から候補語を算出する。
- `rising`（上昇中）と `cooccurring`（一緒に出る）を分けて返す。
- 各候補には値、算出種別、短い機械的説明を付ける。
- 件数の少ない候補や固有名詞・センシティブ語は、閾値と除外辞書で表示を抑制する。

### FR-008: 比較表示

- 比較語は同じ期間・粒度・データソースで集計する。
- 2系列を直接ラベル、線種、テーブル列で識別できるようにする。
- 比較は2語までとし、外部API呼び出しは逐次実行する。
- 「今回の発見」は取得件数と期間別変化から決定的に生成し、取得データで裏づけられない媒体領域や因果関係を断定しない。

## 5. 情報アーキテクチャ

```text
[SC-001 ホーム]
    ├─ キーワード検索 ───────────→ [SC-002 トピック分析]
    ├─ サンプルテーマ ───────────→ [SC-002 トピック分析]
    └─ データについて ───────────→ [SC-004 データと利用条件]

[SC-002 トピック分析]
    ├─ 年代グラフ操作 ───────────→ 同画面更新
    ├─ 関連文脈を選択 ───────────→ 別キーワードで同画面更新
    ├─ 比較語を追加 ─────────────→ 2系列比較で同画面更新
    ├─ 記事カード選択 ───────────→ [SC-003 出典詳細]
    ├─ 別キーワード検索 ─────────→ 同画面更新
    └─ 共有 ────────────────────→ 共有シート / URLコピー

[SC-003 出典詳細]
    ├─ NDLで確認 ───────────────→ 外部サイト
    └─ 戻る ────────────────────→ [SC-002 トピック分析]
```

## 6. 画面仕様

### SC-001: ホーム

- URL: `/`
- 目的: 価値を理解し、最初の検索を30秒以内に開始する。
- P1要素: 一文説明、検索入力、検索ボタン、サンプルテーマ
- P2要素: 3ステップ説明、データ出典、最近の検索
- P3要素: プロダクト背景、FAQ
- 状態: 初期、入力中、送信中、バリデーションエラー

### SC-002: トピック分析

- URL: `/topics/[query]`
- 目的: 掲載傾向と代表記事を理解し、出典確認または共有へ進む。
- P1要素: 検索語、集計期間、件数グラフ、主要数値、収録範囲注記
- P2要素: 代表記事一覧、年代フィルター、関連文脈、比較、共有アクション
- P3要素: 方法論
- 状態: ローディング、成功、部分取得、0件、外部API障害、キャッシュ表示

### SC-003: 出典詳細

- URL: `/records/[source]/[recordId]` またはSC-002内ドロワー
- 目的: 書誌情報・データ提供元・外部リンクを確認する。
- 状態: 成功、項目欠損、リンク切れ

### SC-004: データと利用条件

- URL: `/about/data`
- 目的: 収録範囲、集計方法、ライセンス、免責を説明する。

## 7. 内部API仕様

### API-001: トピック検索

- Method: `GET`
- Path: `/api/v1/topics/search`
- 認証: 不要
- Query:
  - `q`: string、必須、1〜50文字
  - `from`: `YYYY`、任意
  - `until`: `YYYY`、任意
  - `granularity`: `1y | 5y | 10y | all`、任意、既定`5y`
  - `compare`: string、任意、比較語1件
- Response 200:

### API-002: 出典詳細

- Method: `GET`
- Path: `/api/v1/records/[source]/[recordId]`
- 認証: 不要
- Response: 正規化済み書誌情報、外部リンク、ライセンス情報

### API-003: 共有カード

- Method: `GET`
- Path: `/api/og/topic`
- Query: `q`, `from`, `until`
- Response: `image/png`
- 必須表示: キーワード、期間、件数推移、MAGTRACE、データ範囲注記

## 8. データモデル

SupabaseはMVPではAPIキャッシュと共有スナップショットに限定して使用する。ユーザー認証は導入しない。

### テーブル: `api_cache`

| カラム | 型 | NULL | 説明 |
|---|---|---:|---|
| `cache_key` | text PK | NO | 正規化条件のSHA-256 |
| `source` | text | NO | `ndl_zassaku`等 |
| `query` | text | NO | 正規化済み検索語 |
| `params` | jsonb | NO | 年代・粒度等 |
| `payload` | jsonb | NO | 正規化済みレスポンス |
| `fetched_at` | timestamptz | NO | 外部API取得時刻 |
| `expires_at` | timestamptz | NO | 再取得可能時刻 |

インデックス:

- `idx_api_cache_expires_at ON api_cache(expires_at)`

RLS:

- クライアントからの直接アクセスは全拒否。
- Server Route / Edge Functionのみサービスロールで読み書きする。

### テーブル: `share_snapshots`

| カラム | 型 | NULL | 説明 |
|---|---|---:|---|
| `id` | uuid PK | NO | 共有ID |
| `slug` | text UNIQUE | NO | 公開URL用 |
| `query` | text | NO | 検索語 |
| `params` | jsonb | NO | 期間等 |
| `snapshot` | jsonb | NO | 共有時の集計値 |
| `created_at` | timestamptz | NO | 作成時刻 |

RLS:

- SELECT: 全ユーザー許可
- INSERT: サーバーのみ
- UPDATE / DELETE: クライアント禁止

```text
[api_cache]    外部APIレスポンスを正規化・一時保存

[share_snapshots]    共有時点の表示結果を固定
```

## 9. 非機能要件

### NFR-001: パフォーマンス

- キャッシュヒット時の主要コンテンツ表示: p75 1.5秒以内
- キャッシュミス時: 進捗表示を1秒以内に開始
- 外部APIは同時1リクエストを基本とし、年代区分を逐次取得する
- タイムアウト: 8秒。部分結果または再試行導線へフォールバックする

### NFR-002: 外部API保護

- 同一検索条件は最低24時間キャッシュする
- 429・5xxでは指数バックオフする
- bot・大量検索対策としてIP単位のレート制限を設ける
- 生XMLをクライアントへ返さない

### NFR-003: セキュリティ・プライバシー

- 入力値をHTMLとして描画しない
- 外部URLは許可したホストのみ表示する
- 外部リンクに`rel="noopener noreferrer"`を付与する
- 検索語は個人情報を含む可能性があるため、分析ログでは必要最小限とする
- APIキーを使用するPhaseでも、ブラウザやGitへ露出しない

### NFR-004: アクセシビリティ

- WCAG 2.1 AAを満たす
- コントラスト比4.5:1以上
- 全主要操作をキーボードで完結できる
- グラフに表形式の代替データを提供する
- タップターゲット44×44px以上
- ローディング・エラーをスクリーンリーダーへ通知する

### NFR-005: レスポンシブ

- Mobile: 360〜767px
- Tablet: 768〜1023px
- Desktop: 1024px以上
- モバイルでは1カラム、デスクトップでは分析と代表記事を2カラム表示できる

### NFR-006: 観測性

- 外部APIの応答時間、エラー率、キャッシュヒット率を記録する
- 利用者向け画面に内部エラーや外部API URLの詳細を露出しない
- 出典クリック・共有・2回目検索を匿名イベントとして計測する

## 10. UIデザイン方針

- コンセプト: 現代的なカルチャー誌 × 信頼できるリサーチツール
- トーン: 知的、好奇心、余白、押し付けない
- 色: 紙を想起させる暖色系ニュートラル、墨色、朱色アクセント
- タイポグラフィ: UIは可読性の高い日本語ゴシック、見出しは日本語明朝を補助利用
- グラフ: 装飾より比較性を優先し、値・軸・期間を明示する
- 表紙画像に依存せず、文字とデータで魅力を作る
- 共有カードは「断定」ではなく「収録データ上の発見」と表現する

UI方針:
